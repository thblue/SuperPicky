# SuperPicky 批量识别工作流

把一个新拍的鸟片目录跑完「检测 → 评分 → 定星 → 识鸟 → 视频封面入库 → 产出浏览库」，并核对结果后向用户汇报。
完整背景文档：`dev-docs/howto/PROCESS_QUICKSTART.md`（本 skill 是它的可执行浓缩版）。

## 1. 跑前检查

1. **定位目录**：用户可能给完整 UNC 路径（`\\NAS-server\PHOTO\观鸟\2026 观鸟\2026.8 天坛`）
   或只给文件夹名——按名字在 `\\NAS-server\PHOTO\观鸟\` 及其子目录下定位，找不到再问。
2. **确认未处理过**：目录下已存在 `.superpicky/report.db` 说明跑过。首次处理直接继续；
   重跑必须先：① 备份 `report.db` 为 `.superpicky/report.db.bak_<原因>_<时间戳>`；
   ② 确认没有 SPBBrowse/主程序进程开着该目录（编辑中的浏览库不能重跑覆盖）。
3. **统计文件数**：数一下 RAW（CR3/NEF/ARW…）和视频（MP4/MOV/M4V）数量，后面核对要用。
4. **确认 venv**：一律用 `G:\code\SuperPicky\.venv\Scripts\python.exe`，命令加 `-X utf8`。

## 2. 执行（参数已固化，不要自行增减）

```bash
cd G:/code/SuperPicky
.venv/Scripts/python.exe -X utf8 superpicky_cli.py process -i "<目录>" --birdid-country CN -c 40 --birdid-threshold 40
```

- **`-i`（= `--auto-identify`）必须显式加**：识鸟总开关只认这个 CLI 参数、不回落配置。
  漏掉不报错——评分照跑，但鸟种沿用库里旧数据，等于白跑。日志里出现
  `Multi-bird` / `Bird ID` / `Low confidence` 行才是真跑了识鸟。
- **`--birdid-country CN` 是国内目录默认**；海外拍摄按实际国家传（如 `AU`、`SG`）。
  不传时链路是「GPS 反查国 → 兜底 CN」，国内显式传 CN 最稳。
- **`-c 40`（AI 置信度门槛）是本工作流的定档参数**（2026-09-06 用户定档 40，
  50 偏严）：显式传以覆盖配置（当前配置 min_confidence=0.7）。它同时控制
  有鸟判定、V2 排序池入池线和补救扫描的直接救回线，影响星级密度。
- **`--birdid-threshold 40`（鸟种采纳/存储门槛）同为本工作流定档参数**
  （2026-09-12 定档 40；GUI 配置 birdid_confidence 与代码默认值已同步为 40，
  显式传参作双保险）：低于 40% 的候选不定种入库。注意种名错误率随门槛
  降低而上升，跑后对「可疑鸟种」（跨分布物种、40-50% 低置信段）的
  人工复核更重要。
- **视频阶段默认开启**（不需要额外参数）：目录里的 MP4/MOV/M4V 会在照片阶段后
  自动抽「YOLO 置信度最高的有鸟帧」生成封面 `<视频名>_vcover.jpg`，作为普通
  photos 记录入库——有鸟默认 **2 星**（不进 40%/20% 配额定星）、无鸟 -1 不出
  sidecar；封面走多鸟识别，视频作为封面伴生文件一起归入 `{鸟种}/2星_良好/`。
  浏览库里封面即缩略图，改星/改种视频随行，删除连带视频，详情面板可「打开视频」。
  确实不要处理视频时加 `--no-videos`。
- **其余参数一律不传**：锐度/美学/配额/布局/写入模式全部跟随
  `advanced_config.json`（GUI 高级设置改了就跟着变），这正是「跟之前一样」的含义。
  特别注意：V2 配额定星**不消费** `-s/-n` 阈值；2★/3★ 名额密度由配置里的
  `custom_quota3`/`custom_quota2` 控制。
- **长任务放后台**（Bash `run_in_background`），预计 **2-3 秒/张**（RTX 3090 + NAS 实测；
  V5.9.6 触发式细瓦档会让部分批次跑瓦片补救扫描，2026-10-01 乐活中堤 1741 张实测
  3.0 秒/张、总 88 分钟），每隔一两分钟看一眼输出确认在推进即可。
- **启动静默期勿误判卡死**：大头 RAW 目录先跑「DPP 伽马预读」——按 100 张/批调
  exiftool 解析 CanonVRD（1285 张 CR3 ≈ 13 批、每批约 1 分钟），期间 Python 主进程
  CPU 几乎不动、日志因重定向缓冲为空、`.superpicky/` 尚未创建。判据：出现新的
  exiftool.exe 子进程且启动时间在推进 = 正常。预览缓存
  （`.superpicky/cache/temp_preview/` 计数）开始增长即进入主处理阶段。

### 生活照模式（--lite）：个人生活照为主、零星鸟片的目录

适用：目录是按手机型号等归档的个人生活照（如 `\\NAS-server\PHOTO\xiaomi11`、
`\\NAS-server\PHOTO\ip6`），鸟片零星、大部分照片预期无鸟、召回要求低。
这类目录在 `\\NAS-server\PHOTO\` 顶层、不在 `观鸟\` 子树内——第 1 节的
按名字定位搜不到，直接用用户给的完整路径。

```bash
cd G:/code/SuperPicky
.venv/Scripts/python.exe -X utf8 superpicky_cli.py process -i "<目录>" --birdid-country CN -c 40 --birdid-threshold 40 --lite
```

- **`--lite` 语义**：仅本次运行生效、不写 advanced_config.json、鸟片目录
  不受影响。关瓦片全图重扫 + 细瓦档 + 无鸟补救重扫（无鸟照片只跑主扫
  一次 YOLO），视频封面抽帧上限降为 8（默认 60）。识别语义变化：主扫
  低于 -c 40 直接判无鸟、低置信小鸟会漏——这是本模式接受的代价。
- **保留不变**：检出鸟后的识鸟/评分/定星/sidecar/浏览库全链照旧；
  flat 布局 + metadata_write_mode=none 下照片文件零接触。启动输出出现
  `⚡ Lite 生活照模式` 行即生效。
- **跑后核对四步**（不跑第 3 节全量核对）：
  1. 行数对账：photos 行数 == **全部照片（JPG/HEIC/RAW）+ 视频数**——
     手机目录 RAW=0，别按第 3 节之 1 的 RAW 公式算；
  2. 有鸟清单：从 report.db 拉 has_bird 照片与视频封面（种名、张数、
     星级、文件名）直接汇报；未定种回捞（第 3 节之 5）默认跳过
     （召回要求低，用户要时再单跑）；
  3. 种名快速过目：只扫一眼种名清单、排除荒谬误判（生活照背景复杂，
     误判可能很离谱，如室内检出猛禽）；
  4. **可疑种与未定种目视复核（必做，非可选项；第 6 节的轻量版）**：
     - 必检范围：低置信采纳（birdid_confidence < 60%）逐张目检；
       第 6.4 节挂号的误判易感种（白眉歌鸫等）逐种按置信降序抽 1-2 张；
       ≤2 张的零星种全量目检（6.4 第一条同样适用）；
     - 未定种有鸟照片：逐张看图定案——能确认的直接
       `spb_rename_species.py photo` 定种，明显无鸟的
       `photo --wipe --apply` 抹标，看不清的保留未定种（6.3 铁律：
       拿不准禁止硬改常见种名）；
     - 方法：生活照目录多为纯 JPG，原图可直接 PIL 读，无需走预览缓存；
       生成「全帧 + 主鸟框特写」拼图逐张看；拿不准看 ±2 连拍帧。
       不执行第 6 节的星级段抽样与全量遍历。
- **跳过**：第 3 节之 4 的 DPP 伽马核对（无 CR3）、第 3 节之 6 的 EXIF
  缺口回填（metadata_write_mode=none 不写元数据）。
- **速度/磁盘预期**：无鸟照片约 0.2-0.5 秒/张（RTX 3090，仅一次主扫），
  视频每部 8 帧；JPG 不落预览缓存，HEIC 抽预览到 `.superpicky/cache/`
  （浏览库缩略图依赖，删了无鸟 HEIC 就没图）；sidecar 只出有鸟照片。
- **汇报**：以有鸟清单为主（种名+张数+星级+文件名），附行数对账结论与
  处理耗时；星级分布/飞鸟标记等鸟片统计从简。

## 3. 跑后核对（必做，缺一不可）

1. **行数对账**：`report.db` photos 行数 == RAW 文件数 + 视频数（视频封面也是 photos 行）。
   不等 → 在输出里搜「异常被跳过」（NAS 偶发 WinError 5 锁文件）或「视频阶段」失败行，
   被跳过的照片/视频保留旧结果，需补跑。
2. **日志统计**：从输出尾部提取「处理完成统计」（星级分布/飞鸟标记/总耗时）和
   「视频阶段完成」行（封面数/有鸟数/已定种数/无鸟数/已归类数）。
3. **sidecar 对账**：`.superpicky/meta/` 的 JSON 数 == has_bird 数（无鸟照片和
   无鸟视频封面按瘦身策略不导出；有鸟视频封面正常导出）。
4. **DPP 伽马编辑核对**：V5.9.4（W1）起跑批内已「人工优先」消化 DPP 编辑——
   RAW 转换前批量预读 CR3 的 CanonVRD recipe，本次新抽取的预览先套人工 LUT、
   跳过自动提亮不叠加（日志见「DPP 人工伽马编辑 N 张」与逐张 `DPPGAMMA` 行，
   开关 `advanced_config.preview_dpp_gamma` 默认开）。因此：
   - 跑批日志已有 DPPGAMMA 行、且跑批后没再进过 DPP → 本步跳过；
   - 跑批**之后**又做了 DPP 伽马编辑、或处理 V5.9.4 之前的老批次 → 走第 4 节
     （其 `--dry` 只读不动缓存，可放心先用）。
5. **未定种回捞**：`scripts_dev/backfill_species.py "<目录>" --threshold 40`
   （dry）→ 可采纳 >0 就 `--execute`。V5.6 起识鸟门控有替代通道（喙可见或
   YOLO≥0.6 照常识鸟）+ 门控拒绝仍落框行，「零机会」照片已从源头消灭；
   此步兜住残留的：分类置信 <40% 的换跑批时点重试、无检测行旧照片重检。
   采纳清单按 40-50% 段标注复核。跑过伽马重跑（第 4 节③）的不用重复。
6. **EXIF 缺口核对**：`scripts_dev/backfill_rescued_exif.py "<目录>"`（dry）。
   应报「无待回填行」；若列出照片（有鸟但日期为空——无鸟救回/改种链路
   缺口的指纹特征），加 `--execute` 回填（写前自动备份），再跑
   `scripts_dev/reexport_sidecars.py "<目录>"` 重导。视频封面行自本次
   修复起随封面写入拍摄日期（本地墙钟），老批次缺日期的封面也被这一步兜住。

## 4. DPP 伽马编辑重跑（跑批后新做的编辑 / V5.9.4 之前的老批次，顺序不可乱）

```bash
cd G:/code/SuperPicky
D="<目录>"
.venv/Scripts/python.exe -X utf8 scripts_dev/refresh_gamma_previews.py  "$D"            # ① 刷亮缩略图
.venv/Scripts/python.exe -X utf8 scripts_dev/recalc_gamma_scores.py     "$D" --execute  # ② 重算指标（先 dry 看清单）
.venv/Scripts/python.exe -X utf8 scripts_dev/backfill_species.py        "$D" --threshold 40 --execute  # ③ 补种
.venv/Scripts/python.exe -X utf8 superpicky_cli.py rerate-v2 "$D" --min-conf 0.4 --metrics-rebuilt --execute  # ④ 重定星
```

- V5.9.4（W1）起，跑批**前**已存在的 DPP 编辑由跑批内自动消化（人工 LUT 优先，
  跳过自动提亮）；本节只服务两种情况——跑批**后**新做的编辑回补、V5.9.4 之前
  处理的老批次。对已消化的批次实跑本节 ① 幂等无害（重抽原始预览再套同一 LUT，
  产出一致），但 ②③④ 不必空转（④ 的 `--metrics-rebuilt` 无人工改星豁免，
  指标没变就不要跑）。
- **① 刷缩略图**：解析每张 CanonVRD 伽马中点 → 幂律 LUT（`g=2^中点值`）应用到
  `.superpicky/cache/temp_preview/`。幂等（每次从 CR3 重抽原始预览再套 LUT，
  重复跑不叠加）；`--dry` 只读不动缓存；回退 = 删缓存 jpg 自动重生原始版。
  只动缓存，零接触照片/DB。
- **② 重算指标**：用提亮预览按主管线口径（主鸟框+15% padding → 关键点锐度/眼/喙
  → TOPIQ 鸟裁剪区 → ISO 归一化 + 原 caption 对焦权重 + 飞版加成）更新
  head_sharp/eyes/beak/nima_score/adj_* 列。无库内框的照片（当时锐度 0 被识鸟
  门控挡下、没写检测行）自动 YOLO 重检兜底。真糊片（拍摄即脱焦）提亮也救不了，
  维持 0★ 是正确结果，不是流程失败。
- **③ 补种**：未定种照片用亮图重识别（40% 采纳线，人工改种/删鸟自动保护）。
  40-50% 低置信段错误率偏高，采纳清单要进汇报供人工复核。
- **④ 重定星必须带 `--metrics-rebuilt`**：指标已变，rerate-v2 的复现校验
  （分组校验/自校验）前提「指标未变」不成立，不带会被正确拦截。该模式全部
  按新指标重算（无人工改星豁免层），写前自动备份。
- 每步写库前自动备份 report.db；全部完成后再向用户汇报第 4 节结果。

## 5. 汇报格式

向用户汇报：星级分布表（3★/2★/1★/0★/无鸟，2★ 含视频封面数单独注明）、
识出的鸟种及张数（标注罕见度 ○常见/◔能见/◑少见/●传奇）、视频处理情况
（封面数/有鸟数/定种数/无鸟数）、总耗时与速度、对账结论（无丢失）、
第 6 节复核结论（保留/改种/抹标清单及依据，抹标照片进未定种池）、
提醒复核两个点（低置信未定种的数量；可疑鸟种，如跨分布物种可能是误判）。
若走了第 4 节伽马重跑，追加：编辑张数、缩略图刷新、指标重算（None→有值
救回几张）、星级升降清单（逐张 新旧对比）、补种采纳清单（40-50% 段标注复核）。

## 6. 跑批后必做复核（每目录常规分类打星后的固定工序，非可选项）

每个目录跑完常规流程并通过第 3 节核对后，必须按本节对可疑鸟种做目视复核
——不等用户提。多目录批量时**并行化**：B 目录后台跑批期间，对已完成的
A 目录做本节目检（纯 CPU/PIL 读图，不占 GPU，与跑批互不影响）。

1. **必检范围**（逐目录遍历，按 6.3 各定则执行）：
   - ≤2 张有星种全量目检（6.3 第一条，不抽样）；
   - 跨分布可疑种（6.3 清单 + 当地鸟况）按置信度降序 1-2 张；
   - 尾部零星种（数量少、国内不常见）严格复核——拿不准就不定种。
2. **星级段随机抽样**（3/2/1/0★ 各 2-3 张、无鸟 2-3 张、ORF/暗光机型的有鸟
   样本 2 张）为可选加强：用户点名「检查质量」或新管线首跑验证时执行。
3. **看图方法**：`.superpicky/cache/temp_preview/` 的预览是 ≈7000px 超大 JPEG，
   直接图像工具读取会解码失败——先用 PIL `thumbnail((1600,1600))` 缩小存本地
   temp 目录，再起本地 HTTP 服务（`python -m http.server`）逐张视觉核对。
   连拍（相邻文件名 IMG_67xx 连号）按组抽代表张目检，结论共享整组。
   注：把 `report.db` 拷回本地核对时必须连 `-wal`/`-shm` 一起拷——WAL 模式下
   刚写入的数据留在 `-wal` 里，只拷主文件会读到改前旧状态（2026-10-14 踩坑：
   改种明明成功、核对却显示未生效）。
4. **重点核查模式**（2026-10-01 乐活中堤实战教训，共性规律）：
   - **≤2 张有星种全量目检（2026-10-16 用户定则，最高优先）**：每目录某鸟种
     照片 ≤2 张且其中有星的，逐种**真看图**（不许只按分类学/分布规则推断定夺
     ——2026-10-15 教训：曾答复「零星检查了」但欧亚攀雀只按「北京只有中华
     攀雀」改名没看图、角䴙䴘没看图就抹标；补检发现前者芦苇中根本无鸟可辨、
     后者是凤头䴙䴘）。拿不准的连同相机前后帧一起看；有把握的保留，没把握的
     一律抹标留未定种。逐目录遍历，不抽样。
   - **目检分辨率与同位定案（2026-10-16 补充）**：全帧小图不算目检完成——拿
     不准必须重抠**鸟体高清特写**再看（教训：杂色山雀按低清全帧判成绿背山雀，
     高清重看栗红头顶+黑胸带+白腹，实为红头长尾山雀家庭群）；前后帧必须拼在
     一起对比；前后帧有**清晰已定种的其他鸟**、且零星鸟位置未变时，该零星
     标签高度可疑，以清晰帧的种为准。
   - **破坏性删除三条铁律（2026-10-16 贵州麻雀误删复盘）**：species --wipe 是
     整库级（波及该种名下全部主种+背景框），只删「某次改名产生的错标」时必须
     用 photo --wipe 逐张。① 零星标签拿不准就直接抹标，禁止不经目检就按大群
     默认硬改成常见种名——白翅交嘴雀→麻雀 的 9 张错标与 18 张真麻雀同名后，
     species 级清理再也无法区分真数据和错标，一刀下去 21 张全没；② 任何
     --apply 破坏性操作前必须先跑 dry-run 核对波及 photos 数与预期一致，对不
     上就停；③ 破坏性操作的输出必须完整读 JSON（photos/soft_deleted 数字），
     禁止 grep -c 吞掉——误删当晚 grep 只回了「1」，21 张真麻雀被抹无人察觉。
     （另：直接 SQL 修库后必须先 wal_checkpoint(TRUNCATE)，否则 reexport 等
     只读链路读不到新状态。）
   - **跨分布标签 = 远距小主体猛禽误判重灾区**：矛隼(实为游隼/燕隼类)、
     澳洲鸢/栗鸢(实为黑鸢)、白尾鸢(实为鹊鹞/白尾鹞)、沙丘鹤(实为雁属)、
     黑琴鸡(实为雉类)。回捞 40-50% 段还可能带进白翅澳鸦/白眉歌鸫这类新误判。
   - **复合体「半误判」补充判例（2026-10-20 ip6 实战）**：模型在拆分种上
     系统性选欧洲标签——欧乌鸫(实为乌鸫 mandarinus，北京公园常态种 vs
     merula 新疆罕见)、小斑啄木鸟(实为星头啄木鸟，北京无小斑)、白眉歌鸫
     (实为红尾鸫雌型，判据=缺粗白长眉纹与红胁)、斑腰燕(实为金腰燕)。
     遇「北京极罕见+欧洲近缘种」组合先想拆分史：mandarinus/星头/红尾鸫
     均 2008 年前后才从欧洲复合体拆出，分类器两头摇摆，按基准率整批统一。
   - **单张稀有鸟复核法——连拍前后帧当证据（2026-10-14 官厅 11.15 实战）**：
     主种仅 1-2 张、且本地无分布的种（冰岛鸥/赤胸朱顶雀/海鸬鹚这类）不能只
     按置信度抽样，要逐张抠框并把相邻帧（±2 号文件）一起看。三种定案模式：
     ① 前后帧有更清晰角度直接定案（冰岛鸥案：特写见黑翼尖白斑镜斑 →
     排除冰岛鸥 → 普通海鸥）；②「同鸟异标」——同一只鸟在相邻帧被打不同
     标签，以更可信者统一（赤胸朱顶雀案：IMG_7237 标稀有雀科，相邻
     IMG_7235 同鸟同枝标灰伯劳 → 统一灰伯劳）；③ 整群飞行场景的单帧
     跨分布误标，按场景主导种整种统一（海鸬鹚案：4 主种+47 背景框全在
     灰鹤群起飞场景 → 整种改灰鹤）。注意单张稀有 ≠ 必错：小鸥深色小嘴+
     圆翼+翼后缘黑带特征齐全就保留原判。改种用 spb_rename_species（photo
     单张 / species 整种，主种与背景框一起清）；剪影定不了案的（沙丘鹤/
     钳嘴鹳类——当地当时可能有真鸟记录）保留原标签进汇报交用户定夺。
   - **零星混群标签以大群为准（2026-10-15 用户定则，官厅 11.15 落地）**：已知
     大群（如灰鹤群 186 张）的照片流里夹杂的零星异种标签，除非有该种的强识别
     证据（白头鹤白颈、丹顶鹤红冠黑颈、蓑羽鹤浅色羽饰等画面可见），否则一律
     改回大群种；连大群种也对不上的（白色鹤个体、雾中暗影、无锚点小剪影）用
     `photo <目录> <文件名> --wipe --apply` 抹标留未定种，疑似真鸟（如白鹤）
     进汇报交用户定夺。
   - **西方灰伯劳型「半误判」**：识别对象是灰伯劳复合体（黑过眼纹+灰上体+
     白尾端+钩喙都对），只是模型选了欧洲分裂种标签，建议整批改灰伯劳/楔尾伯劳。
   - **Accipiter 属体型区分弱**：雀鹰 16 张中 11 张实为苍鹰——鉴别特征：
     圆弧尾端(中央尾羽最长)+宽长白色眉纹+粗密横纹+粗壮体型=苍鹰；
     平齐尾端+细横纹+窄短眉+小巧轻快=雀鹰。逐组目检后可用
     `spb_rename_species.py photo "<目录>" <前缀> --to-cn 苍鹰 --to-en
     "Northern Goshawk" --to-sci "Accipiter gentilis" --apply` 改种
     （photos+detections+sidecar 三处同步；不改照片 XMP——XMP:Title 是跑批时
     写给 Lightroom 的一次性快照，与 GUI 改种行为一致）。
   - **无鸟判定可信**：抽到的「无鸟」包括鹿/狍等哺乳动物和环境照，均判定正确。
   - **同种高数量簇可能是真的**：黑鹳 169 张经 4 张目检全真（过境群连拍），
     先抽 2-3 张验证再下结论。

## 8. 事后改星 / 补种（常见后续需求）

- **不要用 `superpicky_cli.py restar`**：V2 配额模式下已被代码级禁用
  （执行即拒绝；2026-08-31 事故，详见 dev-docs/reference/cli-reference.md）。
- **重定星用** `superpicky_cli.py rerate-v2 <目录> [--min-conf 0.4 --execute]`：
  不重跑检测/识鸟，从 report.db 重建 V2 定星输入；默认 dry-run，双自校验
  （复现存库评级、人工改星豁免保留 + 鸟种分组校验和）通过后写库，写前
  自动备份并同步 sidecar。改 2★ 名额用 `--quota2`。视频封面行
  （`*_vcover`）自动跳过——封面固定 2 星，改单个视频星级在浏览库手改。
  指标重算过的批次（如第 4 节伽马流程②）必须加 `--metrics-rebuilt`。
- **未定种补种用** `scripts_dev/backfill_species.py <目录> --threshold 40
  --execute`：仅对有鸟未定种的照片按新采纳门槛重识别，镜像写入
  photos / bird_detections / sidecar 三处，dry-run 默认、写前备份。
  低置信候选（40-50% 段）错误率偏高，采纳后建议人工过目。

## 9. 键分裂巡检（中英名与学名打架）

站点按 (中文名, 学名) 分组展示鸟种。photos 行中英名与主检测框
（is_selected=1）学名属不同鸟种时，同一鸟种会被劈成两个条目（2026-10
奥森实例：黄眉柳莺 5 张 + Phylloscopus coronatus vs 24 张 inornatus）。
成因有二：历史管线把 photos 主种与检测行种名写偏；或旧版
`spb_rename_species.py photo` 改种只同步「种名命中旧名」的检测行，
主框种名与 photos 行不一致时主框永远同步不上。

- **巡检用** `scripts_dev/spb_scan_key_splits.py "<目录>"`（只读）：以
  bird_reference.sqlite 为权威映射，列出中英名与学名打架的全部组合；
  退出码 0/1 可作巡检判据。七个 2021-2026 目录 2026-10-17 全扫为零。
- **修复**：photos 行错、检测行对 → `spb_rename_species.py photo` 按
  检测行物种改（2026-10-17 起工具已修：主框无论自身种名是否命中旧名
  一律随照片改写，sidecar 按旧名+主框旧名各跑一轮，幂等）；photos 行
  对、检测行错 → 工具同步不到该行，直接 SQL 更新选中检测行
  species_cn/en/scientific_name 后 `wal_checkpoint(TRUNCATE)`，再
  reexport_sidecars。改前逐张目检定夺，拿不准就 wipe。
- **判例**：稀有种「保留」必须在前后帧证据链上成立（连拍 ±2 号文件），
  代表帧单点判断不够——江西钳嘴鹳 19 张即因只看代表帧而误保留，前后帧
  证实为东方白鹳群+白鹤。
